# 版本与发布

> 茶馆怎么编版本号、怎么起代号、安装包怎么命名、一次发布要做哪几步。
> 版本号、代号和打标签由产品负责人拍板；这一页只记规则和做法。

## 1. 版本号

茶馆用语义化版本（SemVer）：`主版本.次版本.修订号`，例如 `0.1.0`。

| 改了什么 | 升哪一位 | 例子 |
|---|---|---|
| 只修了问题，用法不变 | 修订号 | 0.1.0 → 0.1.1 |
| 加了功能，旧的茶馆、旧的客户端照常能用 | 次版本 | 0.1.1 → 0.2.0 |
| 不兼容的改动：旧客户端连不上新 Relay、仓库结构或座位表的格式变了 | 主版本 | 1.4.2 → 2.0.0 |

- **0.x 是走向 1.0 的阶段**：按 SemVer 的约定，0.x 里的次版本也可以带不兼容的改动。但凡有不兼容，都要在发布说明里写清楚，并告诉用户要不要先升级 Relay。
- **1.0 是对外的承诺**：从 1.0 起，同一个主版本里的客户端和 Relay 互相兼容，茶馆的仓库结构和座位表格式不做破坏性改动。
- 界面、引擎、Relay 用同一个版本号，一起升。

## 2. 代号

- 每一代茶馆有一个代号，是一种茶的名字。**代号只用拉丁字母写，不翻译**（界面、发布页、安装包里都一样），由产品负责人起名。茶的中文名只在 README 里作说明。
- **一个主版本一个代号**：走向这个主版本的 0.x、主版本本身，以及它之后的修补和小版本，都用同一个代号。

| 版本 | 代号 |
|---|---|
| 0.1 … 0.9（第一代的开发阶段，说明书第八节的 M0–M4 在 0.1 里） | **Anji**（安吉白茶） |
| 1.0、1.0.x、1.x | **Anji** |
| 2.0 起 | 下一种茶 |

- 下一种茶最好按字母顺序往后排（Anji 之后从 B 开头的茶里选），这样从名字就看得出先后。这只是建议，以产品负责人起的名字为准。
- 应用图标画的是这一代的茶：Anji 是墨色圆里的一芽二叶（第 6 节）。

## 3. 版本号和代号写在哪里

**唯一的来源**是 `app/package.json`：

```json
"version": "0.1.0",
"codename": "Anji",
```

界面侧栏底部的"v0.1 · Anji"、nightly 发布页的标题都从这里读（`app/vite.config.ts` 的 `__RELEASE__`，`.github/workflows/app.yml` 的发布步骤）。

升版本时，下面几处的 `version` 要和它一起改：

- `Cargo.toml`（工作区，`[workspace.package]`）：引擎、Relay、core 都从这里继承
- `app/src-tauri/Cargo.toml`
- `app/src-tauri/tauri.conf.json`

换代号时，还要改三种语言 README 标题下面的那一行（"v0.1 · *Anji*（安吉白茶）"），并按第 6 节换图标。

## 4. 两种发布渠道

| | nightly（最新测试版） | 正式发布 |
|---|---|---|
| 什么时候 | 每次合并到 `main`，CI 自动构建 | 产品负责人决定发版时，打标签 |
| 在哪里 | GitHub 的 `nightly` 预发布页，每次覆盖 | GitHub 的发布页，一个版本一页，不覆盖 |
| 标题 | `v0.1 Anji · 最新测试版 · 日期 · 提交` | `v0.1.0 Anji` |
| 文件名 | **固定不变**：`teahouse-android-arm64.apk`、`teahouse-windows-x64-setup.exe`、`teahouse-client-windows-x64.exe`（README 里的下载链接指向它们，换版本时不能失效） | 带版本和代号：`teahouse-0.1.0-anji-arm64.apk`、`teahouse-0.1.0-anji-x64-setup.exe` |

- **git 标签只用版本号**：`v0.1.0`，不带代号。
- 本机给用户打的测试包（放进共享文件夹 `安装包/` 的）和正式发布一样，带版本和代号：`teahouse-0.1.0-anji-arm64.apk`。
- 所有安卓包都用同一把签名钥匙（`~/.config/teahouse/android.jks`，CI 用 Secrets 里的同一把），证书 SHA-256 是 `7b4848838eec36757c71729c215d40aac53f3cb8b6363ab74aae727f089e8294`。换钥匙等于逼用户卸载重装，而卸载会丢掉设备钥匙。

## 5. 正式发布的步骤

> **还没有自动化**：现在 CI 只会发 nightly，打标签不会触发构建。第一次正式发布（`v0.1.0`）之前，要给 `app.yml` 加一个"打标签就构建、按第 4 节命名、上传到这个版本的发布页"的任务。

1. **定范围**：产品负责人确认这个版本要包含的东西都已合并进 `main`，nightly 在真机上试过。
2. **改版本号**：按第 3 节改那几处，开一个 PR（标题如"版本 0.1.0"），合并。
3. **打标签**：在合并后的提交上打 `v0.1.0` 并推送。
4. **构建和上传**：CI 构建各平台的包，按第 4 节命名，上传到 `v0.1.0` 的发布页，标题 `v0.1.0 Anji`。
5. **发布说明**：用 GitHub 的"根据合并的 PR 自动生成"生成，再把不兼容的改动、要先升级 Relay 之类的提醒写在最前面。PR 标题本来就按"做了什么"来写，所以自动生成的说明可以直接读。
6. **Relay**：这个版本要求新 Relay 的话，按 [RELAY.md](RELAY.md) 和 `deploy/install.sh` 升级服务器，**先升 Relay，再让用户装新客户端**。
7. **告诉用户**：在真茶馆里说一声：发了什么版本、怎么装（直接覆盖安装，不要卸载）。以后由打包机自动在"安装包"公告下面回一条。

暂时不维护 `CHANGELOG.md`：每个 PR 都改同一个文件会互相冲突，第 5 步自动生成的说明已经够用。等有了第一个正式版本，再决定要不要把发布说明存成文件。

## 6. 应用图标

- 源文件：`app/src-tauri/icons/source.svg`（1024×1024）。界面里的标志 `app/src/lib/Mark.svelte` 是同一份几何，颜色用 `--ink` / `--paper`，夜间模式自动反色。
- 改了 `source.svg` 以后，先渲染出 1024×1024 的 `source.png`，再在 `app/` 里运行 `npx tauri icon src-tauri/icons/source.png`，重新生成各平台的图标；安卓生成在 `src-tauri/gen/android/` 里，再复制到 `src-tauri/icons/android/`。
- 安卓自适应图标的底色是米白 `#F1ECE2`，由 `app/scripts/android-patch.sh` 设置（`tauri icon` 默认是白色）。
