# 身份与连接：茶馆怎么认人，人怎么认茶馆

> 1号写于 2026-10-26。起因：打包机在 GitHub 上连不上茶馆，报"Relay 的主机钥匙变了"；更早的问题 0005 也是同一类。
> 这一页讲四件事：现在怎么验证、出了什么问题、怎么修的、还剩下哪些挑战；最后对照大公司的做法，给出建议。

## 1. 一共有三件事要验证

茶馆没有账号和密码，只有钥匙。一次同步里，其实有三个方向的验证：

| | 谁验证谁 | 用什么 | 在哪里做 |
|---|---|---|---|
| ① | **茶馆认人**：这台设备是不是座位上的人 | 设备钥匙（ed25519）。座位表 `members.toml` 里记着每个人每台设备的公钥 | 服务器上的 OpenSSH + Relay 的强制命令 |
| ② | **茶馆认内容**：这个提交是不是本人写的 | 每个提交都用设备钥匙签名（SSHSIG） | Relay 的 pre-receive：签名的钥匙必须在座位表上（法则第 13 条） |
| ③ | **人认茶馆**：连上的是不是我们自己的服务器，而不是冒充的 | 服务器的**主机钥匙** | 引擎：第一次连接时记下指纹，以后每次核对 |

**① 和 ② 一直正常。** 今天出问题的是 ③。

### ③ 现在的做法：第一次连接时记下（TOFU）

TOFU 是 trust on first use 的缩写，意思是"第一次见面时相信对方，记住它的样子，以后认这个样子"。手机、电脑第一次连上服务器（兑换邀请、配对、或者 `join`）时，引擎把服务器主机钥匙的 SHA-256 指纹写进 `<引擎目录>/known_hosts`。之后每次连接都核对：一样就继续，不一样就拒绝，报"Relay 的主机钥匙变了"（`host_key_changed`）。

拒绝是对的：如果有人在网络上冒充服务器，它拿不出我们服务器的私钥，指纹就对不上。普通的 `ssh` 也是这样做的。

## 2. 出了什么问题

**一台服务器不只有一把主机钥匙。** 我们的服务器同时有 Ed25519、ECDSA、RSA 三把（OpenSSH 默认会生成这几种）。连接时，客户端说"我想要哪几种"，服务器从里面挑一把给它。**不同的客户端要到的可能是不同的那一把，指纹当然不一样。**

而引擎当时只记一个指纹，不记它是哪一种钥匙。于是只要两次连接要到的钥匙类型不同，就会被当成"钥匙变了"：

| 时间 | 现象 | 原因 |
|---|---|---|
| 10-25（问题 0005） | 1号在电脑上兑换邀请成功，接着克隆却报"钥匙变了" | 兑换走引擎自己的 ssh（libssh2），克隆走 libgit2 的 ssh，两者要的钥匙类型不同 |
| 10-25（#49） | 修：让兑换也照 libgit2 的顺序要钥匙 | 两条路要到同一把了，但这个顺序取决于下一行的事 |
| 10-26（打包机） | 打包机在 1号电脑上入座成功；到了 GitHub 的机器上，`join` 报"钥匙变了" | **libgit2 按这台机器的 `~/.ssh/known_hosts` 决定要哪种钥匙**。1号的电脑平时用 ssh 登这台服务器，那里记着 Ed25519，所以要到的是 Ed25519；GitHub 的机器是全新的，没有这个文件，要到了另一把 |

**根本原因**：记下的主机钥匙是哪一种，取决于"这台机器以前用 ssh 连过什么"。同一个人、同一份引擎目录，换一台机器就可能对不上。手机上没有 `~/.ssh`，每次要的都是同一种，所以手机一直没出事；出事的是电脑、CI，以及把引擎目录搬到别的机器上的情况。

**附带的后果**：问题 0001（图片加不进去）里，服务器从来没收到过附件。附件上传走引擎自己的 ssh，很可能也撞上了这个问题。10-26 在修好的引擎上，附件第一次传到了服务器。

## 3. 怎么修的

| PR | 做了什么 | 性质 |
|---|---|---|
| #49 | 兑换和 git 要同一种钥匙 | 修了一半 |
| #64 | 打包机把引擎的错误打印出来，才看到是 `host_key_changed` | 排查 |
| #65 | CI 里先用 `ssh-keyscan -t ed25519` 取服务器的公钥放进 `~/.ssh/known_hosts`，让引擎要 Ed25519 | 绕过（指纹仍由引擎核对，不降低安全性） |
| **#66**（2号） | **根治**：引擎只用一套 ssh（git 也走引擎自己的连接）；`known_hosts` 每行记 `主机 指纹 钥匙类型`，以后只向服务器要这一种；第一次连接按固定顺序要（Ed25519 优先），不看 `~/.ssh`；旧记录只有指纹的，自动逐种试出对应的类型并补上 | 根治 |

#66 测过的情况：本机在没有 `~/.ssh` 的环境下 `join` 成功并补上类型；安卓模拟器上用旧记录升级后配对、同步、推送都成功；打包机在 GitHub 上用新引擎发出了通知。2号的 sshd 集成测试加了 E9（引擎目录换到没有 `~/.ssh` 的机器）和 E10（没有座位的钥匙报 `not_a_member`）。

## 4. 还剩下的挑战

1. **第一次连接是盲信的。** TOFU 的弱点在第一次：如果兑换邀请的那一刻正好有人冒充服务器，引擎会记下假的指纹，之后一直信它。现在邀请码里只有服务器地址（`TH-…@122.10.118.71`），没有指纹。
2. **服务器换钥匙，所有人都会断。** 服务器重装系统、换机器、或者主机钥匙泄露需要更换时，每台设备都会报"钥匙变了"，而且没有安全的办法告诉大家"这是正常更换"。目前只能每台设备手动处理。
3. **"不在座位上"的提示**：#66 之前，被移除的设备看到的是"连不上茶馆"。#66 已改成"Relay 不认识这台设备"，界面上还要配一句人话（"你已经不在这间茶馆的座位上了"）。
4. **被移除的设备签的新提交**：法则第 13 条现在接受"在座位表任何一个版本里出现过"的钥匙，所以设备被移除后，它新签的提交理论上还会被接受。DEVICES.md 第 88 行建议收紧为"推送那一刻必须在座位表上"，还没做。
5. **服务器被暴力猜密码。** 茶馆只认钥匙，猜不进来；但连接太多会触发 sshd 的限流（MaxStartups），偶尔误伤自己人的同步。10-26 一天丢了 18 个连接。用户决定先不管。
6. **继承（v0.2）**：伙计在新的 Relay 上重开茶馆时，新服务器的主机钥匙和旧的不同，客户端怎么确认"这是合法的新家，不是冒充的"？这和第 2 条是同一个问题，而且是说明书第五节里最原创的那部分。

## 5. 大公司怎么做

| 做法 | 谁在用 | 怎么解决"第一次"和"换钥匙" |
|---|---|---|
| **公布指纹 + TOFU** | GitHub、GitLab 的 ssh | 在官网公布主机钥匙指纹，让人第一次连接时核对。2023 年 3 月 GitHub 的 RSA 主机私钥意外泄露，只能全网更换，所有人都看到"钥匙变了"的警告，要手动删旧记录。这说明光靠 TOFU，换钥匙的代价很大 |
| **SSH 证书（主机证书）** | Facebook、Netflix（BLESS）、Uber 等的内部服务器 | 不再信每一把主机钥匙，而是信一个"签发机构"（CA）。服务器的钥匙由 CA 签名，客户端只需预先知道 CA 的公钥。服务器换钥匙时，CA 重新签一张证书就行，客户端不受影响 |
| **TLS 证书（WebPKI）** | 所有 HTTPS 网站 | 浏览器内置一批受信的证书机构，网站的证书由它们签发。第一次访问也能验证，换钥匙对用户透明 |
| **邀请里带着对方的指纹** | Tailscale 的节点钥匙、Magic Wormhole、Signal 的链接设备二维码 | 第一次连接的信任来自"邀请/二维码本身"：里面带着对方钥匙的指纹或一次性的共享秘密，所以第一次连接就能核对，不用盲信 |
| **安全码 + 密钥透明** | Signal 的安全码，WhatsApp 的密钥透明（2023），Apple iMessage 的联系人密钥验证（iOS 17.2） | 用户可以当面比对一串数字；服务端把所有公钥记在一本只能追加、可公开审计的账本里，换钥匙留痕，偷偷换会被发现 |

**共同的原则**：第一次信任最好来自一个已经可信的渠道，而不是网络本身；换钥匙要有一个"旧的为新的担保"的办法；钥匙的类型和指纹要一起记。

## 6. 对茶馆的建议（按先后）

1. **邀请码和配对码里带上服务器主机钥匙的指纹**（类似 Tailscale、Signal 的做法）。邀请本来就是通过微信等可信渠道从老板手里发出的，把指纹放进去，第一次连接就能核对，消除"第一次盲信"。代价：邀请变长一点，可以只带指纹的前 16 位。
2. **用 Relay 自己的签名钥匙为主机钥匙担保。** 服务器上已经有 `relay_signing_key`（用来签邀请产生的座位提交）。让它签一份"本服务器的主机钥匙清单"，客户端第一次连接时记下签名钥匙；以后服务器换主机钥匙，只要清单上有签名钥匙的签名，客户端就自动接受。这相当于一个最小的"SSH 主机证书"，也为第 4 节第 6 条的继承打基础：伙计的新 Relay 可以由老板或旧 Relay 的签名钥匙担保。
3. **界面上把"钥匙变了"讲清楚**：说明这可能是有人冒充，也可能是服务器重装；给出"怎么确认"（问老板要新的指纹）和"确认后怎么办"。不要只显示"连不上"。
4. **收紧法则第 13 条**（DEVICES.md 已有建议），让移除设备立刻生效。
5. 服务器加固（fail2ban 之类）等以后再说。

第 1、2 条要改邀请格式和 Relay，属于协议层，需要产品负责人拍板、2号来做；说明书第五节的 v0.2 继承设计可以和第 2 条一起考虑。
