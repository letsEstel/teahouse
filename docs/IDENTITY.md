# 身份与连接：茶馆怎么认人，人怎么认茶馆

> 1号写于 2026-10-26，同日按产品负责人的意见改写成大白话。
> 起因：打包机在 GitHub 上连不上茶馆，报"Relay 的主机钥匙变了"；更早的问题 0005 也是同一件事。

## 一句话

**出问题的不是"茶馆认不认得你"，而是"你认不认得茶馆"**：手机、电脑、打包机连服务器时，要确认连上的真是我们自己的服务器。确认的办法有个漏洞，换一台机器就可能把真服务器当成冒牌货。现在已经补上（#66）。

## 1. 每次同步，其实在核对三件事

把茶馆的服务器想成一家**只认熟客的店**：

| | 谁核对谁 | 用什么 | 好比 |
|---|---|---|---|
| ① | 店认人：你是不是座位上的人 | 你每台设备上的钥匙；座位表里记着每把钥匙 | 店员看你的会员卡 |
| ② | 店认内容：这条修改是不是你本人写的 | 每个提交都用你的钥匙签名 | 每张单子上都有你的签字 |
| ③ | **人认店：这家店是不是真的那家，不是冒牌的** | **服务器的"主机钥匙"** | **你记住真店门口的样子，下次去先对一眼** |

①和②一直正常。**这次出问题的是③。**

### ③ 是怎么做的

第一次连上服务器时（兑换邀请、配对），你的设备会把服务器"门口的样子"拍张照存下来（主机钥匙的指纹，存在引擎目录的 `known_hosts` 里）。以后每次去都对一眼：对上了才进门；对不上就停下，报"主机钥匙变了"。

对不上就停是对的：如果有人在网络上冒充我们的服务器，他拿不出我们服务器的钥匙，门口的样子就不一样。普通的 ssh 也是这样做的。

## 2. 这次是怎么发生的

**关键事实：这家店有三扇门，三扇都是真的，但长得不一样。**

我们的服务器同时有三把主机钥匙（Ed25519、ECDSA、RSA 三种，装系统时自动生成）。连接时，客户端先说"我想走哪种门"，服务器就开那扇门给它看。

**问题在于：设备只拍了门的照片，没记"这是哪扇门"；而它下次走哪扇门，取决于这台机器的习惯。**

这个"习惯"来自这台机器上 ssh 的历史：如果这台机器以前用 ssh 登过这台服务器（`~/.ssh/known_hosts` 里有记录），引擎里负责同步的那部分（libgit2）就会优先走那扇门；没有记录，就按自己默认的顺序走。

打包机就是这样被拦下的，一步一步：

1. **在 1号的电脑上入座。** 1号的电脑平时用 ssh 管服务器，习惯走 **Ed25519 门**。于是打包机第一次连接时，拍下的是 Ed25519 门的照片。
2. **把钥匙和照片一起存进 GitHub。** 打包机以后在 GitHub 的机器上干活。
3. **GitHub 的机器是全新的，没有任何习惯**，按默认顺序走了 **ECDSA 门**。
4. **一对照片：对不上。** 打包机以为遇到了冒牌服务器，停下来，报"主机钥匙变了"。

其实服务器一直是同一台，只是换了扇门。

**为什么手机一直没事？** 手机上没有 ssh 的历史，每次都走同一扇门，照片永远对得上。

**问题 0005 是同一件事，发生在同一台电脑里面。** 当时引擎内部有两套连接的办法：兑换邀请用一套，同步用另一套（libgit2），两套的习惯不一样。1号兑换邀请时拍了 A 门，紧接着同步时走了 B 门，就被拦下了。附件上传用的也是"兑换"那一套，所以图片一直传不上去，很可能也是这个原因。

## 3. 怎么修的

| 时间 | PR | 做了什么 | 性质 |
|---|---|---|---|
| 10-25 | #49 | 让兑换和同步走同一扇门 | 修了一半：走哪扇还是看机器的习惯 |
| 10-26 | #64 | 让打包机把错误打印出来，才看清是"照片对不上" | 查原因 |
| 10-26 | #65 | 打包机出门前，先把 Ed25519 门写进 GitHub 机器的"习惯"里 | 临时绕过 |
| 10-26 | **#66（2号）** | **照片背面写上"这是哪扇门"，以后只走这扇门**；引擎只留一套连接办法；第一次连接固定先走 Ed25519 门，不再看这台机器的习惯；旧照片没写门的，自动试出是哪扇门再补上 | **根治** |

#66 测过：在"全新机器"上能连上；安卓模拟器从旧记录升级后，配对、同步、写留言都正常；打包机在 GitHub 上已经连续几次正常回帖。

## 4. 还没解决的

1. **第一次是盲信的。** 第一次连接时，设备拍下的是"当时看到的门"。如果恰好在那一刻有人冒充服务器，设备会拍下假门，以后一直信它。现在的邀请码里只有服务器地址，没有"真门长什么样"。
2. **服务器换门，所有人都会被拦。** 服务器重装系统、搬到新机器、或者钥匙泄露要换，每台设备都会报"主机钥匙变了"。而且没有安全的办法告诉大家"这是正常换门"，只能一台一台手动处理。
3. **继承也会撞上这件事。** 说明书第五节说，伙计可以在新的服务器上重开茶馆。新服务器的门和旧的不一样，大家的设备怎么确认"这是伙计开的合法新店，不是冒牌货"？这和第 2 条是同一个问题。
4. **被移除的设备签的新提交**：法则第 13 条现在只要求签名的钥匙"在座位表的某个版本里出现过"，设备被移除后，它新签的提交理论上还会被接受。DEVICES.md 已有收紧的建议，还没做。
5. **服务器被暴力猜密码。** 茶馆只认钥匙，猜不进来；但连接太多会触发限流，偶尔误伤自己人的同步。产品负责人决定先不管。

## 5. 专业的做法

解决"第一次怎么信"和"换门怎么办"，业内有这几种做法：

| 做法 | 怎么做 | 解决了什么 | 例子 |
|---|---|---|---|
| **公布门的样子** | 在官网上公布服务器的指纹，第一次连接时让人自己核对 | 第一次可以不盲信，但要靠人去对 | GitHub、GitLab 的 ssh。2023 年 GitHub 的一把主机钥匙泄露，只能全网换门，所有人都看到"钥匙变了"的警告、手动处理，说明这种做法换门很痛苦 |
| **邀请里附上门的样子** | 邀请或二维码里直接带着服务器的指纹 | 第一次就能自动核对，不用盲信；邀请本来就是通过可信的渠道（微信、当面）发的 | Tailscale 加设备、Signal 关联新设备的二维码、Magic Wormhole |
| **找一个担保人** | 服务器的门由一个"担保人"签字（证书）。设备只记住担保人的签名样子；换门时担保人在新门上签字，设备看到签名就放心 | 换门对用户透明，不用一台台处理 | 所有 HTTPS 网站（浏览器内置担保人）；大公司内部服务器用的 SSH 证书 |
| **公开账本** | 所有钥匙都记在一本只能往后写、谁都能查的账本上；偷偷换钥匙会被发现 | 防止服务器自己（或被攻破后）偷换 | WhatsApp 的密钥透明、iMessage 的联系人密钥验证、Signal 的安全码 |

共同的原则：**第一次的信任要来自一个已经可信的渠道，而不是网络本身；换钥匙要有一个"旧的为新的担保"的办法；钥匙的种类和样子要一起记。**

## 6. 对茶馆的建议（按先后）

1. **邀请码和配对码里附上服务器的指纹**（"邀请里附上门的样子"）。邀请本来就是老板通过微信等可信渠道发出的，把指纹放进去，第一次连接就能自动核对，消除盲信。邀请会长一点，可以只放指纹的一部分。
2. **让服务器自己的签名钥匙当担保人**（"找一个担保人"的最小版本）。服务器上已经有一把 `relay_signing_key`（现在用来签邀请产生的座位记录）。让它为服务器的门签字，设备第一次连接时记住这个签名；以后服务器换门，只要有它的签字，设备就自动放行。继承时，新服务器也可以由老板或旧服务器担保，这正好为说明书第五节的 v0.2 打基础。
3. **界面上把"钥匙变了"讲成人话**：可能有人冒充，也可能是服务器重装；告诉用户怎么确认（问老板要新的指纹），确认以后怎么办。不要只显示"连不上"。
4. **收紧法则第 13 条**，让移除设备立刻生效（DEVICES.md 已有建议）。
5. 服务器加固（fail2ban 之类）以后再说。

第 1、2 条要改邀请的格式和服务器，属于茶馆协议本身，需要产品负责人拍板，由 2号来做。
