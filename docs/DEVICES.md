# 一人多设备 · Several devices per member（座位表格式提案）

> 状态：**已确认**（用户 2026-10-20，评审方同意）。2 号提案。决定见第 7 节。
> 背景：用户同时用手机和电脑，这是 v0.1 必需的。INVITE.md 第 2 节第 8 条（设备配对）把格式留到这里定。

## 1. 要满足的事

1. **每台设备一把钥匙，钥匙不出设备。** 新设备自己生成钥匙；旧设备的私钥不导出、不复制（CLIENT-API 第 2 节）。
2. **一个人还是一个成员。** 手机和电脑上是同一个成员 id、同一个座位；签名、留言、提案都算这个人的。
3. **丢了手机能补救。** 从另一台设备就能把丢的那台移除，不用找老板，也不用重新入座。
4. **普通人不碰钥匙。** 加设备 = 在旧设备上点"添加一台设备"，得到一个配对码，在新设备上粘贴。
5. **旧的座位表照样有效**，历史里已有的版本不用改写。

## 2. 格式

成员的第一台设备仍然写在 `key` 里；更多的设备写成顶层的 `[[device]]` 表，用 `member` 指向成员：

```toml
version = 2

[teahouse]
name = "梧桐里三号院"

[[member]]
id = "wang"
name = "王阿姨"
role = "host"
key = "ssh-ed25519 AAAA…"          # 第一台设备（电脑）

[[device]]
member = "wang"
name = "手机"                       # 可选：给人看的设备名，最多 32 个字
key = "ssh-ed25519 AAAA…"
```

**为什么是 `[[device]]`，而不是 `keys = [...]` 或 `[[member.key]]`**（INVITE.md 第 8 条提过的两种写法）：
- 座位表的解析器（`teahouse-core::toml`）刻意只认一个很小的 TOML 子集：没有数组，没有嵌套表。这个文件决定谁能写茶馆，所以"看不懂就拒绝"比"猜"安全。`[[device]]` 用的正是已经支持的写法，**解析器一行不用改**；另两种都得放宽解析器。
- 设备要有名字（"手机""电脑"），移除的时候才认得出来。数组里的一串钥匙放不下名字；TOML 注释也不会被保留。

**兼容**：
- 没有任何 `[[device]]` 的座位表照旧写成 `version = 1`，和今天一字不差；只有真的多了设备，才写成 `version = 2`。
- 新的 core 两个版本都读；旧版本的 Relay 和客户端遇到 `version = 2` 会明确报"unsupported format version 2"，不会误读。
- 引擎内部把一个成员看成"一组设备"：`key` 是第一台，`[[device]]` 是其余的。移除了写在 `key` 里的那台时，写回文件时下一台顶上去。

## 3. 法（拟加入规则表，第 18、19 条）

| # | 法 |
|---|---|
| 18 | 一个成员可以有多台设备：`key` 加上所有 `member` 指向他的 `[[device]]`，**每人最多 5 台**。每个 `[[device]]` 必须指向一个存在的成员。所有钥匙在整张座位表里唯一，只收 ed25519。用其中任何一把签名的提交，都算这个成员的（第 13 条）。 |
| 19 | 设备的增减：老板照常可以改座位表的任何部分（第 8 条）。此外，**成员本人**可以：用配对码给自己加一台设备；从任意一台自己的设备移除自己的另一台设备。这两种由 Relay 代写提交（作者是成员本人，提交者是 `Teahouse Relay`，用 Relay 的钥匙签名，带 `Act: seat` 和 `Device: <add\|remove> <设备名>`），并经过和推送相同的全部检查。每个成员任何时候至少保留一台设备。 |

## 4. 配对和移除（Relay 命令）

| 命令 | 谁 | 做什么 |
|---|---|---|
| `pair [--name 手机] [--minutes 10]` | 任何已入座的钥匙 | 生成一个配对码 `TH-…`，默认 **10 分钟**有效（最长 60），只能用一次。对这把钥匙在这个 Relay 上入座的**所有茶馆**都有效。 |
| `redeem <配对码> --name <设备名>` | 新设备（陌生钥匙，走 `redeem-shell`） | 在每一间茶馆里，给发码的那个成员追加这台设备。输出每间茶馆的 `house <id>` 和 `member <id>`。 |
| `unpair <茶馆> <设备名或钥匙指纹>` | 成员本人 | 移除自己的另一台设备。不能移除最后一台。 |

- 配对码和邀请码是同一种码、同一套存储（只存哈希）、同一套限速和审计（`pair.created`、`pair.redeemed`、`pair.failed`、`device.removed`）。
- **为什么对所有茶馆有效**：一个人常常坐在好几间茶馆里，手机要一次进全部；他在不同茶馆里的成员 id 可以不一样，Relay 按发码那把钥匙逐间找到他的座位。
- **10 分钟、只能用一次**：码只是在自己的两台设备之间搬一下，不需要长期有效；被人看到也很快作废。

## 5. 引擎和界面

- 引擎命令：`pair { house? }` → 配对码（`TH-…@relay`）；`redeem` 原样接受配对码（界面不用区分邀请码和配对码）；`devices { house }` → 我的设备列表；`unpair { house, device }`。
- `Member` 增加 `devices?: { name: string; added: string; thisDevice: boolean }[]`，只对自己的座位给出（别人的设备不必显示）。
- **同一个人两台设备的同步**：两台都是完整副本，照常同步。只有一种情况需要特别处理：两台设备在离线时**改了同一个提案**。这时引擎不再强推覆盖，而是把本机这一份另存为一个新提案（名字加后缀），再告诉用户。
- "我是谁"：本机钥匙是某个成员的任何一台设备，就是这个成员。

## 6. 丢了设备

- **丢了一台、还有别的**：在另一台上 `unpair` 丢的那台。之后丢的那台连不上 Relay，签名也不再被接受（第 13 条看的是座位表上出现过的钥匙，见下面"要定的事"第 2 条）。
- **全丢了**：找老板。老板在座位表里给这个成员换上新设备的钥匙（第 8 条），或者重新邀请。

## 7. 已定的事（2026-10-20）

1. **每人最多 5 台。** 用户说 15 台也可以；先定 5 台，以后放宽不会破坏任何现有座位表，收紧却会，所以从小的开始。
2. **收紧第 13 条**：新推送的提交，签名钥匙必须在推送那一刻的座位表上；历史里的旧提交不再重新检查。
3. **配对码对所有茶馆一起生效。**
4. **AI 成员可以配对。**

## 7a. 原来要定的事

1. **每人最多 5 台**，够不够？
2. **被移除的设备以前签的提交还算不算数**：今天的第 13 条接受"在座位表任何版本里出现过"的钥匙，所以移除之后，那台设备**以前**签的提交依然有效（这是对的，历史不该变）。但它**之后**再签的新提交也会被接受。建议把第 13 条收紧为：**新推送的提交，签名钥匙必须在推送那一刻的座位表上**；历史里的旧提交不再重新检查。这样移除就立刻生效。这一条也会影响已经离座的成员：他们之前签好、还没推送的提案，离座后就推不上去了。这与 CLIENT-API 第 8 节第 5 条一致（导出交还给本人）。
3. **配对对所有茶馆一起生效**，还是一次只配一间茶馆。我建议一起生效（第 4 节）。
4. **AI 成员能不能配对**：按照第 17 条"标记不限制角色"的精神，应该允许；一个 AI 在两台机器上跑，也是同一个成员。
