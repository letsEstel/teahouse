# 它防得住什么，防不住什么

一个安全系统最诚实的文档，是写清楚它**防不住**什么。这种分析叫**威胁模型**（threat model）：先问敌人是谁、能做什么，再问系统怎么应对。不写威胁模型的“安全”只是一种感觉。

维护茶馆的人必须把这一节记在心里。每次改动 Relay，都要问：这张表上的哪一格变了？

## 谁是对手

茶馆假设了这几种人：

| 对手 | 他有什么 | 他想做什么 |
|---|---|---|
| 外人 | 网络连接 | 进来看，进来写 |
| 茶客 | 一把有效的钥匙 | 超出权限：写别人的东西、改规则 |
| 伙计 | 一把权限更大的钥匙 | 给自己升职 |
| 老板 | 最大的权限 | 改写历史，抹掉说过的话 |
| 丢手机的人 | 一台被别人拿走的设备 | |
| Relay 的运营者 | 服务器的 root | 看内容，篡改 |

注意老板也在对手名单上。一个系统如果只防外人，一旦内部的人起了坏心就全完了。茶馆的目标是让老板的权力**有边界、留痕迹**。

## 防得住的

| 攻击 | 挡在哪里 | 代码 |
|---|---|---|
| 外人连接 | 没有座位的钥匙，只能兑换邀请 | `relay/src/shell.rs` |
| 试探茶馆是否存在 | 不存在和无座位回答相同 | `NOT_FOUND` |
| 茶客直接写 main | 只能新增自己的留言 | `guest_change_refused` |
| 伙计改座位表 | 路径规则 | `may_write_on_main` |
| 冒充别人写提交 | 作者必须和签名一致 | `check_signatures` |
| 老板强制推送 | 只能前进，不能改写 | `is_ancestor` |
| 用 `.TeaHouse/` 这样的路径冒充 | Windows 和 macOS 不分大小写时才生效 | `is_reserved_lookalike` |
| 留言时间戳作弊 | 显示顺序按进入 main 的先后，文件名里的时间不起作用 | 法则第 12 条 |
| 用大推送拖垮服务器 | 提交数、分支数、包大小都有上限 | `MAX_COMMITS_PER_PUSH` |

其中“冒充路径”这一格值得细看，因为它告诉你攻击者是怎么想问题的：

```rust,ignore
// core/src/rules.rs
pub fn is_reserved_lookalike(path: &str) -> bool {
    let first = path.split('/').next().unwrap_or("");
    if first == ".teahouse" {
        return false;
    }
    let normalised = first.trim_end_matches(['.', ' ']).to_ascii_lowercase();
    normalised == ".teahouse" || normalised.starts_with(".teahouse:") || normalised == "teahou~1"
}
```

在 Linux 服务器上，`.TeaHouse/x` 和 `.teahouse/x` 是两个不同的路径，看起来和座位表毫无关系。可是在 Windows 上它们是同一个目录，文件名末尾的点和空格也会被忽略，`TEAHOU~1` 是它的旧式短名。如果放行，一次推送就可能在别人的电脑上覆盖座位表所在的目录。

这种漏洞来自**两个系统对同一个字符串的理解不一样**。git 自己历史上就出过这类漏洞。设计安全检查时，要站在每一个会读这份数据的系统的角度去想。

## 防不住的

下面这些，茶馆今天防不住。这不是疏忽，每一条都是有意识的取舍，而且写在 README 里：

**Relay 的运营者看得到内容。** 仓库在服务器上是明文。要防这一点就要端到端加密，而那样 Relay 就读不懂内容，所有法则都没法执行。这是一个根本的矛盾。茶馆选择了可执行的规则，代价是你必须信任运营 Relay 的人。

**Relay 的运营者可以拒绝服务，可以删库。** 但他删不掉你设备上的副本。这是每人一份完整副本存在的意义：伙计可以在新服务器上重开，历史完整保留。

**Relay 可以改写历史，或者向不同的人展示不同的历史。** 哈希链让这件事留下证据：你设备上的旧提交和它给的新历史对不上。但今天的引擎不会为此报警。同步时遇到分叉，它把本地多出来的提交重放到 Relay 的版本上。证据还在你的副本里，只是没有人告诉你。这是一个已知的缺口，是值得你动手的第一批改进之一。

**丢了设备，钥匙就在别人手里。** 钥匙存放在设备上，没有密码保护。挽救的办法是从另一台设备上移除它，或者请老板调整座位。所以应用会提醒你至少配对两台设备。

**老板可以踢人、改座位表。** 这是老板的权力。系统保证的是这些动作都留在历史里，不保证老板是个好人。

## 边界在哪里

把上面合起来，茶馆提供的保证可以用一句话说清楚：

> 在 Relay 诚实的前提下，只有座位表允许的写入才能进入 `main`；即使 Relay 不诚实，它也无法在不留下证据的情况下改动已经到达你设备的历史。

前半句靠法则，后半句靠 git 的哈希链和每人一份副本。注意后半句说的是“留下证据”，不是“阻止”，也不是“自动发现”。一个维护者应该能背出这句话，并且知道它的每个词为什么在那里。

## 这一节学到的

- 威胁模型要写明对手是谁，以及防不住什么。
- 老板也是对手：权力要有边界、留痕迹。
- 很多漏洞来自两个系统对同一份数据的不同理解。
- 可执行的规则和端到端加密有根本的矛盾，茶馆选了前者。

## 练习

假设要加一个新功能：“老板可以删除一条提交”。对照这一节，这个功能会破坏哪些保证？如果用户真的需要删掉不该公开的内容，你会怎么设计？

<details>
<summary>答案</summary>

它破坏“历史只增不改”，也破坏哈希链：删除一个提交，后面所有提交的哈希都变了，每个成员的副本都会和 Relay 分叉。而且其他人手里仍然有内容，所以删除并不真的有效。

茶馆的做法是**在最新版本里移除，历史里留下这次移除的记录**，老板和伙计删留言就是这样。需要从服务器彻底删除的附件，附件不在 git 里，可以 `blob-purge`，引用文件还在，历史不受影响。这正是当初把附件放在 git 之外的原因之一。
