# 全景：从一个问题到三万行代码

读一个大项目，最容易犯的错误是从第一个文件的第一行开始。代码是答案，不知道问题就看不懂答案。这一篇从最高处往下走：先问茶馆要解决什么，再看为了解决它不得不做哪些决定，最后才落到代码。

无论你属于哪一种读者，都请先读这一篇。后面每一节都是在给这里的某一格填细节。

## 第一层：问题

一小群人要把一件事办成，比如一个小区要解决停车位。他们通常有一个群聊。三个月后，群里有几万条消息，却回答不了三个最基本的问题：

1. 现在有哪些事要办？办到哪一步了？
2. 办成的东西在哪里？最新版是哪一份？
3. 谁说了算？谁能改什么？

群聊的结构是一条时间线，新消息把旧消息推走，什么都留不住。这不是群聊做得不好，而是时间线这种结构不适合做这件事。

茶馆的回答是给这个小团体三样东西：一张人人看得见的问题表，一个存放成果的地方，一套事先约定、自动执行的规则。

## 第二层：决定

前两样不难，难的是第三样。“规则自动执行”这几个字一旦当真，后面一连串决定就都被逼出来了。

**规则要有人执行，所以需要一个裁判。** 如果规则只写在每个人的软件里，改一改软件就能绕过去。规则必须由一个不在用户手里的地方来判。这个地方叫 **Relay**。

**但裁判不能成为命门。** 如果所有东西只存在 Relay 上，它一关，茶馆就没了；运营它的人也掌握了所有人。所以每个成员的设备上都有一份完整的副本，Relay 只是大家会合的地方。这样服务器可以被关掉，茶馆还在。

**有了很多副本，就要解决同步和历史。** 这正是 git 解决过的问题。一间茶馆就是一个 git 仓库，一次写入就是一个提交。git 还送来一个性质：每个提交由内容算出的哈希命名，并且包含上一个提交的哈希，改动历史中的任何一点，后面所有的名字都会变。历史不能被悄悄改写，这件事不靠承诺，靠数学。

**裁判要知道谁是谁。** 账号和密码意味着要保存一份密码库，那是最值得被偷的东西。茶馆的做法是：每台设备自己生成一对钥匙，私钥从不离开设备，公钥写在座位表上。座位表本身就是仓库里的一个文件，所以“谁有什么权限”也有完整的历史。

**规则不能自己改自己。** 如果一次推送可以同时修改座位表、又按新座位表来判断自己合不合法，任何人都能给自己升职。所以 Relay 永远按**推送之前**的座位表来判决。

这五个决定互相咬合，抽掉任何一个，其余几个都要重想。读后面的代码时，你会反复遇到它们。

还有一个数字要单独说：**十五个座位**。这个上限和性能无关，git 撑得起 Linux 内核那样成千上万人的项目。十五是一个组织上的判断：人再多，这群人就要开始分工、开会、分层级，不再是一个一起办事的团体。所以这个数字写进了法则，由 Relay 强制执行。事情更大的时候，答案是再开一间茶馆，而不是把这一间开大。

## 第三层：不造轮子

写一个安全系统，最危险的代码是自己写的代码。茶馆尽量站在经受过几十年攻击的东西上：

| 需要 | 用的是 | 从哪年开始接受考验 |
|---|---|---|
| 认证和加密传输 | OpenSSH | 1999 |
| 存储、同步、历史 | git | 2005 |
| 拦截和判决 | git 的 hook 机制 | 2005 |
| 签名 | ed25519 | 2011 |

所以 Relay 没有自己的网络服务，也不解析网络协议。它在两个地方接上去：OpenSSH 确认钥匙之后调用它，git 接受提交之前调用它。它只做一件别人没做过的事：**按座位判决**。

这种思路有一篇经典论文：Saltzer 和 Schroeder 在 1975 年的《计算机系统中的信息保护》。它列出的原则今天依然成立，茶馆用到了其中四条：

- **机制要简单**（economy of mechanism）：要审计的代码越少越好。Relay 不用任何第三方库，每一行决定谁能进门的代码都在这个仓库里。
- **默认拒绝**（fail-safe defaults）：拿不准的一律不放行，而不是一律放行。
- **每次都检查**（complete mediation）：每一个提交、每一个路径都要过一遍，不因为“这个人刚才检查过”就放过。
- **权限最小**（least privilege）：茶客只能写自己的留言，伙计碰不到座位表。

## 第四层：四个部件

```text
  ┌────────────────── 成员的设备 ──────────────────┐
  │                                                │
  │   app/        界面     Svelte + TypeScript     │
  │     │ 调用                                     │
  │   client/     引擎     Rust，本地副本、签名、同步│
  │     │                                          │
  └─────┼──────────────────────────────────────────┘
        │ ssh + git
  ┌─────┼──────────────── 服务器 ──────────────────┐
  │     ▼                                          │
  │   sshd        OpenSSH，不是我们写的            │
  │     │                                          │
  │   relay/      守门人   Rust，零依赖            │
  │     │                                          │
  │   core/       规则     Rust，纯函数，无 I/O    │
  └────────────────────────────────────────────────┘
```

`core/` 同时被 `relay/` 和 `client/` 使用，所以它画在服务器一侧并不完全准确：它是两边共用的法律条文。

| 目录 | 约多少行 | 依赖 | 是什么 |
|---|---|---|---|
| `core/` | 2500 | 无 | 座位表、钥匙、规则 |
| `relay/` | 7000 | 只有 `core` | 服务器上的守门人 |
| `client/` | 11000 | libgit2 等 | 每台设备上的引擎 |
| `app/` | 8500 | Svelte、Tauri | 界面和手机、电脑外壳 |

依赖的方向只有一个：外层依赖内层，`core/` 什么都不依赖。这个方向决定了读代码的顺序，也决定了哪里出错影响最大。

## 第五层：一条留言的一生

把所有部件串起来。王阿姨在问题 0001 下面写了一条留言，点了发送：

1. **界面**把文字交给引擎，只调用一个命令 `note`。界面不懂 git，也不懂 ssh。
2. **引擎**在本地副本里写一个文件 `talk/0001/<时间>-wang.md`，做一个提交，提交说明里写上 `Problem: 0001`，用这台设备的私钥签名。
3. 这时留言已经在她的设备上了，断网也不会丢。引擎接着尝试推送。
4. **ssh** 连到服务器。sshd 用公钥确认对方确实持有私钥，然后不让她运行任何别的东西，只运行 `teahouse-relay shell <钥匙>`。
5. **Relay 的 shell** 查座位表：这把钥匙在这间茶馆有座位吗？有，就把自己替换成 `git receive-pack`。
6. **git** 把新提交收进隔离区，这时 `main` 还没动，然后运行 `pre-receive` hook。
7. **Relay 的 hook** 查这个提交：签名对不对？作者是不是她？有没有 `Problem:`？这个问题存在吗？她是茶客，改动是不是只新增了自己的留言？时间戳有没有快过服务器十分钟以上？
8. 全部通过，git 移动 `main`。其中任何一项不通过，整次推送作废，引擎收到原因，界面显示出来。
9. 别的成员下一次同步时，收到这个提交。从此它存在于每个人的设备上，内容、签名和它在历史中的位置都在手里。

这九步里，你的代码只出现在 1、2、3、5、7、9。其余的都是别人的、更老的、被攻击过更多次的东西。

## 接下来怎么走

这本书就是沿着这张图往下走：

- **第一部分**讲电脑和程序本身。如果你没写过程序，这里是地基。
- **第二部分**讲 Rust 和别的语言不同的地方，这些地方正好是安全系统最需要的。
- **第三部分**回到这张图，一层一层拆开 Relay，直到你能自己设计这样的系统。

往下读的时候，如果忘了某段代码是干什么的，回到这一页找到它在图上的位置。
